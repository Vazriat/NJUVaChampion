## v2.3 相对 v2.2 的变化

### 1. 段位审核支持一键提醒

段位审核一直是"管理员看得见、选手不知道"的状态：名单列出来了，但没人通知选手去补认证，全靠群里喊。

现在活动管理（分组弹窗）和赛事详情页的段位审核面板，右上角多了「一键提醒」：

- 一次给**当前名单里的所有选手**发站内消息，标题「请更新段位认证」
- 文案分两种：没认证过的提示"还没有通过段位认证"；认证过期（审核时间早于活动创建）的提示"请重新提交最新段位"
- 消息点开直接跳 `/verify` 认证中心
- 已点过「通过」的、段位仍有效的选手**不会收到**——名单是实时算的，不是发的时候拍快照
- 点击前有确认框，明确告诉你这次会发给多少人；发送后提示实际送达人数

接口：

| 方法 | 路径 |
|---|---|
| POST | `/api/admin/competitions/{id}/rank-review/notify` |
| POST | `/api/admin/tournaments/{id}/rank-review/notify` |

返回 `{ sent: N }`。

### 2. 手动分组界面显示队伍评分 + 一键排序

分组时最需要的信息是"哪几支队强"，之前得开另一个页面查评分榜，再凭记忆分组。

现在「队伍分配」里每支队伍名下多一行：

```
评分 4928 · 神话1 / 超凡3 / 超凡2 / 钻石3 / 钻石1
```

评分口径与 `/api/admin/teams/ratings` 一致：队内段位最高的 5 人，各自段位分值相加；不足 5 人按黑铁（1 分）补齐。

标题右侧的排序按钮三态循环：

`按评分排序` → `评分 ↓ 高到低` → `评分 ↑ 低到高` → 恢复原序

排序**只改显示顺序**，不改变任何已选的分组结果，也不会自动做蛇形分配。

### 3. 修复：段位认证"点不动"

**现象**：认证中心里点「段位认证」卡片，只出现一条空边框，看不到段位下拉和提交按钮。用户描述成"按钮点不动"。

**根因**：`certifications.status` 实际有 6 种值，前端只处理了 4 种。

| 状态 | 含义 | 修复前 |
|---|---|---|
| `PENDING` | 待审核 | 显示"审核中"，展开区空白 |
| `APPROVED` | 已通过 | 正常 |
| `REJECTED` | 已驳回 | 正常 |
| `DELETED` | 用户删除 | 正常 |
| `REVOKED` | 管理员撤销 | **显示"未申请"，展开区空白** |
| `SUPERSEDED` | 被新申请取代 | **显示"未申请"，展开区空白** |

最常见的触发场景是段位认证被管理员撤销过。身份认证、裁判认证有同样的问题，一并修了。

修复后：

- `REVOKED` → 「✘ 已撤销」+ 提示 + 重新提交表单
- `SUPERSEDED` → 「已失效」+ 提示 + 重新提交表单
- `PENDING` → 「⏳ 审核中」+ 提示（不显示表单，避免重复提交）
- 取记录时按 `PENDING > APPROVED > 最新一条` 排序，不再盲取第一条历史记录

## 技术要点（面向开发）

| 问题 | 处理 |
|---|---|
| 通知发给谁 | 直接复用 `listCompetitionReview` / `listTournamentReview` 的返回值，名单与面板所见完全一致；override 过的用户在计算阶段就被排除 |
| 通知会不会产生幽灵消息 | 不会。`notifyPending` 标了 `@Transactional`，与业务操作同事务，失败一起回滚 |
| 通知类型 | 新增 `UserNotification.TYPE_RANK_REVIEW_REQUIRED`，`refType=CERTIFICATION`；`type` 字段长度 40 够用 |
| 评分数据来源 | 复用现有 `/api/admin/teams/ratings?sort=score`，前端一次性拉全量建 `teamId → rating` 映射，不新增接口 |
| 排序会不会改变分组 | 不会。`assignment` 是 `Record<teamId, groupIndex>`，与渲染顺序无关 |
| 为什么评分要补黑铁 | 沿用后端 `toRatingVO()` 的口径：不足 5 人补黑铁，保证不同队伍可比 |
| 认证记录为什么不能取第一条 | 后端 `getMyCertifications` 按 `createdAt` 倒序返回**全量历史**，最新一条可能是已撤销的旧记录 |

改动文件：

- `backend/.../service/RankReviewService.java`、`controller/AdminRankReviewController.java`、`entity/UserNotification.java`
- `frontend/lib/api.ts`、`components/CompetitionManager.tsx`、`app/admin/tournaments/[id]/page.tsx`、`app/notifications/page.tsx`
- `frontend/app/verify/page.tsx`
- `docs/api.md`、`AGENTS.md`

数据库：无结构变更（`rank_review_overrides`、`user_notifications` 均为已有表）。接口：新增 2 个 POST。

## 注意事项 / 已知限制

1. **通知不去重**。同一个管理员隔天再点一次「一键提醒」，名单里的选手会再收到一条。前端有确认框，但后端没有"同活动 + 同用户 N 天内只发一次"的限制。
2. **评分会把未认证选手按黑铁计**。待审核选手多的队伍评分偏低，这是评分口径的固有特性，不是 bug。分组时建议结合段位明细一起看。
3. **排序不参与分组决策**。它只是把列表重排，方便从上往下按顺序分配；不会自动按种子蛇形分组。
4. **段位审核列表仍然不阻断分组与开赛**。v2.3 只加了"能通知"，没有加硬性门槛——管理员仍可带着未审核名单直接分组。
